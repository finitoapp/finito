# 0001 The product library is its own repository and deployment, read through a versioned contract

Status: accepted
Date: 2026-11-16

## Context

The product library (`docs/product-library.md`) is data, not app code: a few
hundred gastro products with names, synonyms, related products, VAT per
country, starter packs and pictures. It changes on its own rhythm (a new
product, a better picture, a corrected VAT) and every installed Payky and
Finito reads it, including builds months old that nobody updates. Its
pictures are generated by AI and need a person's approval, and its VAT values
an accountant's. The apps' e2e flows and documentation screenshots must not
change because the live library did.

## Decision

- **The library lives in its own repository**
  (`github.com/finitoapp/product-library`) **and its own Vercel project**,
  published as static files: `v1/library.json` and the pictures under
  `v1/img/`. Its production host is `https://product-library-chi.vercel.app`;
  nothing there runs at request time.
- **`/v1/` is a contract that only grows.** Within `v1` the library may add
  fields, products, categories, packs, languages and countries at any time;
  renaming or removing a field, or changing what it means, is a `/v2/`
  published beside `/v1/`, which stays for the app builds already out
  there. The contract's source of truth is the library's `contract/v1.ts`.
- **The apps read it tolerantly.** Core's `ProductLibrarySchema` names only
  the fields the apps use and drops the rest, so an addition breaks no
  build. It reads the categories, products and packs one entry at a time:
  an entry that breaks the contract, or that the apps could not store (a
  product id longer than the 255 characters a catalog item keeps), is left
  out, and the lists naming it skip it as they skip an unknown id. An empty
  picture reads as none. Only a file whose top level breaks what they read
  (`version`, `imageSizes`, the three lists) fails, as a typed error, which
  the apps treat as no library (catalog/0005).
- **Library ids are permanent.** A catalog item stores one
  (catalog/0006); the library never renames or reuses an id, and a product
  it drops is published `retired`: still resolvable, never suggested,
  related or packed.
- **The library carries no prices**, and only pictures a person approved;
  its VAT values are confirmed by an accountant before a release.
- **Each app reads the host from its environment, defaulting to
  production** (Finito's `EXPO_PUBLIC_PRODUCT_LIBRARY_BASE_URL`), and the
  e2e builds point it at the mock server, which serves no library: flows
  and screenshots run without suggestions, pictures or starter packs, and
  never depend on what the live library holds.

## Alternatives considered

- Keeping the library in this monorepo: every product or picture would be
  an app release, and the data would reach only builds made after it.
- A search API or a database: rejected by catalog/0005; static files need
  no server, no monitoring and no consent.
- A strict reader that refuses unknown fields: every addition to the
  library would break the builds already installed.

## Consequences

- A change to the library ships when it merges to the library's `main`,
  independent of the apps' releases, and a library pull request gets a
  Vercel preview the apps can be pointed at (behind Vercel's login), both
  once the Vercel project is connected to the repository.
- A `v2` means the apps learn it in a release while `v1` stays published
  until no supported build reads it.
- The library's own `bun run check` validates the data (unknown or retired
  ids where they would be offered, duplicate names, pictures without
  approval); this repository's tests hold the reader side.
- No e2e flow covers the suggestions, pictures or starter packs yet; one
  needs the mock server to serve a fixture library.
