# Agent Guide

## Commands

- `bun run check` before handing work back. It is `check:lint` (Biome) + `check:ts` (`tsc -b`, tests included) + `check:decisions` (decision records name the tests that hold them, see `docs/decisions/README.md`) + `check:tests` (Vitest); run those individually while narrowing a failure.
- `bun run format` applies Biome's fixes; `bun run test:watch` reruns Vitest on change; `bun run check:coverage` writes a report to `coverage/`.
- `bun run dev` starts the web-app and landing Vite servers; the web-app runs over HTTPS with a self-signed cert (`PAYKY_DISABLE_BASIC_SSL=1` turns that off for Android live-reload).
- End-to-end tests are not part of `check` and need their own run — see "E2E Testing" below.
- `bun run release` cuts a release from `main` (or a `hotfix/*` branch): it commits the next CalVer `YY.M.MICRO` into `package.json` and pushes the `v<version>` tag that ships it. Leave `version` alone otherwise; `docs/releases.md` has the whole flow.

## Project Rules

- Write all code, comments, commit messages, and documentation in English.
- Business decisions are recorded in `docs/decisions/<domain>/`, one file per decision, each naming the tests that hold it under `## Enforced by` (format in `docs/decisions/README.md`). Read the decisions of a domain before changing its behavior. A change that reverses or narrows a decision adds a new record and marks the old one `Status: superseded by <domain>/NNNN` instead of rewriting it, and a new business rule gets its own record.
- Commit messages follow Conventional Commits: `type(scope): imperative summary`, lowercase, no trailing period. Types in use are `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `chore`; the scope names the module or feature touched (`refactor(payment):`). The subject says what changed and the body says why — put the reasoning there, not in the subject.
- Error reporting goes through `apps/web-app/src/core/sentry.ts` and is opt-in per device (`errorReportingEnabled`, driven by `SentryController`). Report unexpected crashes only: `captureReportedError` has exactly two sanctioned call sites: `AppEvoluConsumersFailed` in `apps/web-app/src/App.tsx`, the boundary around the background consumers of the app Evolu client, and `apps/web-app/src/components/app/error-boundary.tsx`. Never pair it with a `toast.error` or any other handled failure — an expected `Result` the UI already shows the user is not a crash. Events are scrubbed of recovery phrases and IBAN-shaped strings, but keep secrets out of error payloads rather than relying on that.
- Use Bun for dependency management and scripts. Keep `exact = true` in `bunfig.toml`.
- Keep the app TypeScript-first and preserve strict compiler settings.
- Use shadcn-style local UI components in `apps/web-app/src/components/ui`; primitives must come from Base UI.
- `apps/web-app/src/components/ui` and `apps/landing/src/components/ui` (shadcn) and `apps/web-app/src/components/reui` (ReUI) are vendored third-party code, kept byte-for-byte as upstream ships them so a registry re-add stays a clean overwrite. Never edit, shrink, or delete anything in them — not an unused export or variant, not a lint nit; update only by re-adding from the registry (`shadcn` CLI, ReUI MCP). An audit flagging these directories is a false positive; adapt the call site instead.
- Use Zod for form, domain, and Evolu schema validation.
    - Read and write JSON strings through `jsonCodec(schema)` from `packages/core/src/zod-utils.ts`, not `JSON.parse`: `z.safeDecode` returns malformed JSON as an ordinary failed result, so callers need no `try`/`catch`. Write the same value back with `z.encode(codec, value)` so a stored column has one definition for both directions. A one-way `JSON.stringify` (a hash input, an outbound protocol payload, a debug dump) stays as it is. Tests may use `JSON.parse`.
- Store persistent application data through Evolu. Use direct `localStorage` only for per-device UI state that must not sync and is harmless to lose — the language, the home-screen mode, the landing redirect flags.
- Use Biome for linting and formatting.
- Dates split two ways, and both sides are deliberate — don't hand-roll either with `padStart` and `getMonth() + 1`:
    - **Locale-aware display** the user reads goes through `Intl`/`toLocale*`, usually one of the `format*` helpers in `apps/web-app/src/lib/format-utils.ts`.
    - **Date arithmetic and fixed machine formats** go through `date-fns`: `subDays`, `subMonths`, `isSameDay`, and `format(date, "yyyy-MM-dd")`. Its format tokens are locale-independent, which is exactly what a filename, an API parameter, or a stored `DateString` needs.
- Declare environment variables in a `createEnv` block (`@t3-oss/env-core`) with a Zod schema, as `apps/web-app/src/core/app-env.ts` (client, `VITE_*`), `apps/cli/src/cli-env.ts` (CLI) and `buildEnv` in `apps/web-app/vite.config.ts` do, rather than reading `process.env` / `import.meta.env` at the point of use. One variable does not justify skipping it — the point is that every variable is validated and defaulted in one place. A serverless handler reads its env per request through `loadServerEnv` (`apps/web-app/src/server/server-env.ts`), so a missing value answers that request instead of failing the cold start.
- Do not create or use `index.ts` barrel files for re-exporting. Import directly from the owning module file.
- For asynchronous reads from remote or native APIs in React, use TanStack Query's `useQuery` rather than `useEffect` with local state. Use a stable `queryKey` and `enabled` for runtime or input preconditions; keep Evolu subscriptions on `useEvoluQuery`.
- Each `useEvoluQuery` suspends on its own query, so a component reading several waits for them one round trip after another. A screen that reads several starts them all first with `usePreloadEvoluQueries` (`usePreloadDeviceEvoluQueries` for the device database), listing the queries its hooks read too — `billStateQueries`, `paymentRefundsQueries` and the like sit beside those hooks for that. Evolu sends them as one message and each `useEvoluQuery` below awaits the same promise; a query the list misses costs one round trip more, nothing else.
- `@dedalik/use-react` (a VueUse-style hook collection) is a deliberate dependency and stays, however few hooks are imported today. Reach for it before hand-rolling a hook over a browser API, and wrap it where its shape does not fit (`useScreenWakeLock` over `useWakeLock`). A local hook sharing a library hook's name (`useNow`, `useDebouncedValue`, `useLocalStorageState`, ...) diverges on purpose — read its doc comment before swapping it out.
- To keep a per-keystroke/per-frame value from re-rendering an expensive subtree, hold it in a component-scoped Jotai atom and pass the **atom itself** down as a prop. `AmountKeypad` (`apps/web-app/src/features/shared/amount-keypad.tsx`) is the reference implementation, and its doc comment has the measurement that justifies it:
    - Create it with `const [valueAtom] = useState(() => atom(initial))`, never `useMemo` — React may discard a memo and mint a fresh atom, losing the value.
    - Components in between only pass it on; leaves that render it call `useAtomValue`, write-only ones `useSetAtom`, and an event handler that reads it without re-rendering uses `useStore().get(valueAtom)`.
    - Plain `useState` stays the default. Never remove an existing instance of this pattern without measuring first.

## Glossary

- `docs/glossary.md` defines the domain words and the pairs that are easy to mix up — terminal/home/pos, item/catalog item, bill line/payment line, the two meanings of "account", owner. Read it before naming a new module, table, route or translation key, and use its names.


## Workspace boundaries

- `apps/web-app`, `apps/landing`, `apps/cli` and `apps/native-shell` are private Bun workspaces; `packages/core` owns the shared domain. Keep root scripts as the public entry points.
- Core imports no application source, UI frameworks, browser bootstrap or Capacitor implementations. Its internal imports are relative; consumers use explicit `@payky/core/...` subpaths. Node runtime and testing helpers have separate entry points.
- Root `bun run build` emits core JavaScript before the web build; `bun run check:api` verifies production Node resolution. `apps/web-app/vercel.json` is the deployment configuration; Vercel's project root must be `apps/web-app` with outside workspace inputs enabled. `apps/native-app/vercel.json` deploys Finito's PWA with the same API, each handler re-exported from `apps/native-app/api` (`docs/finito-deployment.md`).
- Keep the root CalVer, lockfile, patches, docs, decision identifiers and release automation at the root. Native output is `apps/web-app/dist-native`, distinct from the web deployment's `dist`.

## Project Structure

- `apps/web-app/src/main.tsx` is the browser entry point. It installs polyfills and renders the React app.
- `apps/landing` owns the independently deployed marketing documents at `/landing`, built and prerendered with `bun run build:landing` (landing/0012). Its Vercel configuration maps the existing language and document paths; `apps/web-app/vercel.json` proxies them to the corresponding edge or production landing upstream. `packages/web-shared` owns shared browser navigation, language options and hooks. Keep landing runtime imports independent of `apps/web-app` — the one exception is the apps' generated mockup images, which `landing-mockups.ts` imports by brand; see `docs/landing-deployment.md`. All landing markup must render without a browser and hydrate identically. `PAYKY_LANDING_BRAND` builds it as Payky's, under `/landing`, or Finito's, at the root of finito.fit (landing/0013, `src/core/landing-sites.ts`); its copy names the app and its hosts through placeholders, like the app's.
- `apps/web-app/src/polyfills.ts` is what `main.tsx` imports first: it installs Evolu's own polyfills and `apps/web-app/src/polyfills/android-webview-locks.ts`, which fakes the `evolu-one-tab-sharedworker-polyfill` lock that Android WebView's `navigator.locks` cannot grant. `packages/core/src/testing/setup.ts` installs the Evolu polyfills for Vitest, which is configured in `apps/web-app/vite.config.ts` (`test.exclude` keeps `e2e/**` out of the unit run).
- `apps/web-app/src/App.tsx` wires top-level providers (Jotai store, theme, background jobs, toaster) and the TanStack Router provider.
- `apps/web-app/src/router.tsx` creates the TanStack Router from `apps/web-app/src/routeTree.gen.ts`; route files live in `apps/web-app/src/routes`.
- `apps/web-app/src/routes/__root.tsx` defines the root layout and error boundary; `apps/web-app/src/routes/error.tsx` throws on purpose, in every build, so the error screen and Sentry reporting can be tried on a real device — keep it; `apps/web-app/src/routes/_terminal.tsx` is the layout route for the terminal pages; a route reaches it through `staticData` — `terminalLayout` for its viewport classes, and `menu` (`{ tab, root? }`) to join the menu section, whose bar and sidebar, Home first, `_terminal.tsx` draws from `apps/web-app/src/components/menu-nav.tsx` (`docs/decisions/navigation/0001`; `router.test.ts` fails on a section route without it). Keep route files thin: a route declares itself and renders one feature `*Page`, which draws the whole screen, `FadeHeader` included. Sibling screens that share a header and tabs are the one exception: a layout route renders a feature `*Layout` that draws them once around an `<Outlet />`, so the tabs stay mounted and their indicator slides (`apps/web-app/src/features/activity/activity-layout.tsx`; native's `app/activity/(tabs)/_layout.tsx` over `ScrollAwayHeader`). `apps/web-app/src/router.test.ts` fails on a route that imports `FadeHeader`, the sign of a page written inline or of a wrapper around a feature component that is not a page.
- `apps/web-app/src/atoms` contains Jotai atoms that bootstrap app singletons: the device Evolu client and its migrations (`device-migrations.ts`), the app Evolu client, the active account, the PIN session (`access.ts`), the service proxy consent reader (`service-proxy.ts`), console, run, the global confirm-dialog queue, and the Jotai `store.ts` itself. Evolu clients are created here, not in `main.tsx`.
- `apps/web-app/src/hooks` contains the React bindings for those singletons (`useEvolu`, `useEvoluQuery`, `useDeviceEvoluQuery`, `useConsole`, `useTranslation`, `useAppRun`, ...). Access Evolu from React through these hooks. It also holds hooks more than one feature uses (`useProductLookup`, `useScannerTorch`, ...); a hook only one feature uses lives in that feature's folder, as `apps/web-app/src/features/bill/use-*.ts` do.
- `apps/web-app/src/features` contains feature modules: page-level UI (forms, hooks, presentational components) for one feature, composed from domain modules and `apps/web-app/src/components/ui` primitives. Substantial page UI extracted from routes belongs here, not in `apps/web-app/src/routes` or `apps/web-app/src/components` — `apps/web-app/src/components` holds only app-lifecycle infrastructure and genuinely cross-feature presentational UI. The features: `terminal-home` (the home screen's pos and numpad modes), `bill` (the cart), `activity` (payment and bill histories and their detail screens), `catalog` (the catalog items, categories and tables under `/catalog`), `notifications` (the screen behind home's bell, an empty state for now), `payment-tip` and `payment-wait` (the steps after Charge), `withdraw`, `stats`, `settings`, `onboarding`, and `shared` (below).
- `apps/web-app/src/components/ui` contains shadcn-style reusable UI primitives built on Base UI, such as `button.tsx`. Keep generic UI here; avoid feature or domain logic in this directory. Vendored — see the project rule above.
- `apps/web-app/src/components/reui` contains components vendored from the ReUI registry (`alert.tsx`, `stepper.tsx`, `timeline.tsx`). Vendored — see the project rule above.
- `apps/web-app/src/features/shared` holds what more than one feature needs: option tables and copy (the fiat-currency and UI-language lists, which both settings and onboarding offer), and the small components and hooks two features share (`bank-account-input.tsx`, `refund-badge.tsx`, `use-eet-settings.ts`, ...). Its `forms/` holds the form blocks the catalog and settings share: `form-card.tsx` and the `inline-edit-*` controls. A feature must not import from a sibling feature's folder; if two need the same thing, it moves here (or to `apps/web-app/src/components` when it is a cross-feature presentational component with no feature logic). The split: a shared component that carries domain types or knowledge (`table-tile.tsx` takes an `OpenBillRow`, `category-filter-bar.tsx` a `CategoryFilter`, the account blocks in `shared/account/`) lives here; one that does not (`scan-code-scanner.tsx`, the camera and nothing else) lives in `apps/web-app/src/components`. A folder under `apps/web-app/src/features` is a feature with screens of its own, never a parking place for blocks other features use — that is what this folder is for. `apps/web-app/src/features/feature-boundaries.test.ts` fails on an import from one feature folder into another, `shared` included as a source, and on any import from `apps/web-app/src/components` or `apps/web-app/src/hooks` into `apps/web-app/src/features`, which sit below it.
- `apps/web-app/src/components` holds two kinds of thing, and a new file belongs to one of them: the root is for cross-feature presentational UI (`fade-header.tsx`, `search-input.tsx`, `list-skeleton.tsx`, ...), and `apps/web-app/src/components/app` is for the app and shell infrastructure mounted once — the singletons `App.tsx` mounts (`app-background-jobs.tsx`, `confirm-dialog-host.tsx`, `error-boundary.tsx`, `e2e-test-bridge.tsx`, ...) and the access gate the `_terminal` layout mounts (`access-gate.tsx`, with the `pin-screen.tsx` it shares with `pin-prompt-host.tsx`). Feature UI belongs in `apps/web-app/src/features`, not here.
- `apps/web-app/src/components/theme-provider.tsx` is an app singleton left at the root because vendored `ui/sonner.tsx` imports it from that path; don't move it.
- `packages/core/src/evolu` contains Evolu client setup, the app schema composition, and the device database (`device-client.ts`, `device-account.ts`). Device-database writes are not Tasks but synchronous, fire-and-forget functions here taking `deviceEvolu` and an optional `MutationOptions` (`selectAccount`, `recordPinAttempt`, ...) — they raise no domain errors and the bootstrap atoms write before any run exists. Add a new device write as such a function, not as an inline `deviceEvolu.update` in a component. Register new Evolu tables and indexes in `packages/core/src/evolu/schema.ts`.
- `packages/core/src/modules` contains domain modules. Each module owns its schema, branded ids/types, actions, queries, and tests for one domain concept.
- `packages/core/src/modules/shared` contains lower-level domain helpers, shared schemas, Evolu dependency helpers, and the `getFirstOr` Result helper.
- `packages/core/src/deps.ts` declares small injectable dependency objects (`FetchDep`, `DateDep`, `EvoluOwnerDep`); `packages/core/src/error.ts` provides the `defineError` factory.
- `packages/core/src/background-jobs` contains the background job framework (`BackgroundJobContext`, keyed task queue) and the sync jobs under `jobs/`. `background-jobs.ts` groups them, and each app group runs under its own component in `app-background-jobs.tsx`: `appBackgroundJobs`, `cashuBackgroundJobs`, and `bankBackgroundJobs` (Fio, MONETA), mounted only while the device can reach the banks (in a browser, every open tab with the consent runs them, as another device would); `cliBackgroundJobs` is the CLI's. Jobs receive all effects — including `lockManager` — through their context; never use ambient globals such as `navigator.locks`. A job raises notifications through `NotificationsDep` (`notifications.ts`, held in memory, never stored; `docs/decisions/notification/0001`), and each notification type needs a renderer in both apps (`notification-renderers` in web's and native's `features/notifications`), which `satisfies Record<JobNotificationType, ...>` enforces.
- `packages/core/src/integrations` contains one folder per external service, including this app's own `api/` endpoints (`donations/`, `contact/`). `payky-app/` is the account request protocol between Payky and Finito on one phone (account/0008). `fio/` and `moneta/` read bank account history (`docs/payment-sync.md`; MONETA's VIP API, one merchant token, `docs/decisions/moneta/`). Neither answers a CORS preflight, so a browser reaches them through `service-proxy/`: its registry (`service-proxy-services.ts`: each service's fixed origin, the paths its client calls, the headers passed on), which the bank clients take their base URLs from, and `createServiceProxyFetch`, which the browser's `FetchDep` wraps to send their calls to `/api/proxy/<service>` while the device allows it (`deviceSettings.serviceProxyEnabled`, read per call; `docs/decisions/service-proxy/0001`). The native apps and the CLI call them directly. `qerko/` drives a card terminal remotely and serves Qerko payments over Qerko's POS websocket (`docs/qerko.md`): a config dep carrying only the `Pos-Id`, with the environment (production or sandbox) passed with the credentials of each call and the key read per role (`loadQerkoCredentials(role)`, qerko/0007); the websocket is `QerkoSocketDep` (`qerko-socket.ts`, a service dep over the global `WebSocket`) under the protocol session of `qerko-rpc.ts`, held by the connection job on the one device chosen for it. Every HTTP JSON client goes through `appFetchAsJson` from `packages/core/src/deps.ts` — or `fetchAndValidateJson`, which combines it with the schema check, or `validateJsonResponse` on a response it fetched itself — validates responses with zod, and reports failures as `defineError` errors carrying `status` and `responseBody`. Three are not JSON over HTTP and are exempt: EET speaks SOAP/XML through `FetchDep` directly, nostr talks to relays over WebSocket, and so does Qerko's POS websocket. A client with a configurable host or credentials also exports a dep factory (`createFioApiDep` rotates tokens over a base URL, `createYadioApiDep` carries one); `lnurl-pay-client.ts` derives its host from the Lightning address it is handed — a withdrawal's, a donation's, or the merchant's own `lightningAddress` account, whose invoices it asks for and whose LUD-21 verify it polls (`docs/decisions/lightning-address/`; `fake-lightning-address-wallet.ts` stands in for such a wallet in tests, the demo and e2e) — and the clients of this app's own `api/` take it from `appEnv.VITE_PAYKY_API_BASE_URL`, absolute because the native app's origin has no `/api` of its own. Integration deps come in two shapes, by the nature of the service: a request-per-call HTTP API is a config dep plus Task functions (`createFioApiDep`, `createYadioApiDep`), and a stateful or long-lived connection is a service object with methods (`EetApiDep.submit`, `NostrDep`'s relay pool, `QerkoSocketDep`, `SwitchioTerminalDep`). Either way the dep's type sits next to its factory.
- `packages/core/src/spark` wraps the Spark wallet SDK behind `SparkWalletDep`. Do not call `SparkWallet.initialize`/`getOrCreateWallet` directly outside this wrapper; extend the wrapper when a consumer needs more of the SDK surface. Instances are pooled per mnemonic and ref-counted (`createRefCountedResourcePool` in `packages/core/src/utils/ref-counted-resource-pool.ts`, behind `createSharedSparkSyncWallet`/`createDefaultSparkPaymentWallet`): dispose your own `sparkWallet.create()` result as usual, but the SDK instance itself is torn down only once every holder — the Spark sync job's long-held reference included — has released it, so a warm instance survives back-to-back calls for the same account. `apps/web-app/src/server/donate-wallet.ts` is the one sanctioned exception: stateless per-request server code with no long-lived process to pool for.
- `packages/core/src/migrations` contains the data migrations the app runs at start; `migrations.ts` holds the runner and two ordered registries — `deviceMigrations` over the device database, run by `deviceMigrationsAtom` before the active account is read, and `appMigrations` over the active account's app database, run by `AppMigrations` — and its `Migration` doc comment says what `hasWork` and `run` must guarantee. A migration lives in its own file (`account-derived-id-migration.ts`) that exports one `AppMigration` or `DeviceMigration`, with its test beside it. Everything it needs only for itself — queries, row types, derivations, the writes — stays inline in that file, even when that makes it long: it is single-use code that gets deleted with the migration, so don't extract its pieces into helpers or into the domain modules. Reuse a module's existing exports freely; the one piece worth a local function is the work plan `hasWork` and `run` both read, so the two cannot disagree.
- `packages/core/src/demo-data` generates the fictional history of a demo account (`docs/decisions/demo-data/0001`): `demo-data-generator.ts` composes the domain Tasks at a simulated time with fakes for every outside service and EET left unset, and `demo-data-content.ts` holds the café it describes. A demo account (`account.demo` in the device database) never syncs and runs no background jobs; `DemoDataSeed` in `apps/web-app/src/components/app` runs the generator. It dates rows in the past through `evolu.setMutationBackdate`, which `patches/@evolu%2Fcommon@8.27.2.patch` adds to Evolu — an Evolu upgrade has to carry that patch over (`bun patch`), and `packages/core/src/evolu/evolu-backdate-patch.test.ts` fails when it is lost.
- `packages/core/src/ai` is the in-app assistant (`docs/decisions/ai/`): its model dep, the tools that read the repository docs and source (the git checkout in the CLI, the build's snapshot in the app), and the conversation loop. `packages/core/src/modules/shared/payky-uri.ts` parses the app's own `payky:` URIs, such as device pairing.
- `apps/cli/src` contains CLI-runtime helpers (`cli-env.ts`, the in-process lock manager, and `cli-evolu.ts`, the app Evolu on a Node SQLite file); CLI entry points live in `apps/cli/src/`. The Node Evolu driver and in-process lock manager live behind `packages/core/src/runtime` entry points. Tests open an in-memory one through `createEvoluTest` in `packages/core/src/testing/evolu.ts`, beside the other test helpers there.
- `apps/web-app/api` contains Vercel serverless functions (see `apps/web-app/vercel.json` for routing): the donation feature's `apps/web-app/api/donations.ts` and `apps/web-app/api/lnurlp/donate.ts`, both built on `apps/web-app/src/server/donate-wallet.ts`; `apps/web-app/api/contact.ts`, which forwards the landing contact form over nostr; `apps/web-app/api/support-team.ts`, the support chat's team; `apps/web-app/api/eet/playground-certificates.ts`; and `apps/web-app/api/proxy/fio.ts` and `apps/web-app/api/proxy/moneta.ts`, the service proxies built on `apps/web-app/src/server/service-proxy.ts`, which answer their own origin only (plus `PAYKY_SERVICE_PROXY_ALLOWED_ORIGINS`) and log nothing. `apps/web-app/src/server` holds the code only they run, and `apps/web-app/api/_http.ts` (`jsonApi`) the JSON responses and CORS preflight every handler but the service proxies answers with. `apps/web-app/api/ai/v1/chat/completions.ts` is the assistant's OpenAI-compatible proxy, which holds the AI provider and its key (`docs/decisions/ai/0001`).
- `apps/web-app/src/platform` contains Capacitor/WebView runtime detection (`runtime.ts`) and platform plumbing (`haptics.ts`; `nfc.ts`, the Android NFC reader Bolt Card taps go through). `switchio.ts` wraps the SwitchioPay card terminal, whose ECR protocol is Android-intent-only — the native half is a local Capacitor plugin at `apps/native-shell/android/app/src/main/java/me/payky/SwitchioPlugin.java`, registered in `MainActivity.java`. There is no PWA equivalent: an `intent://` launch returns its result to the browser, not to the page, so card payments are hidden outside `Capacitor.isNativePlatform()`. A result that arrives after Android killed the app mid-payment comes back as a Capacitor `appRestoredResult` event, which `apps/web-app/src/components/app/switchio-restored-result.tsx` settles. `account-share.ts` wraps `AccountSharePlugin.java`, the Android half of the account request Finito sends Payky on the same phone (`docs/decisions/account/0008`): `AccountShareActivity.java` is a UI-less trampoline in the requester's task, `apps/web-app/src/components/app/account-share-request-host.tsx` opens `/settings/accounts/share` for a request, and Finito's side is `apps/native-app/modules/payky-account-request`. The answer carries the master key: never store or log it.
- `packages/core/src/cashu` holds the Cashu payment method over the wallet Payky shares with Linky (`docs/cashu.md`, `docs/decisions/cashu/`): the shard store, the cashu-ts wrapper, counters, restore, topup claim, token receive, melt, autoswap, the NUT-18/BIP-321 request, and a fake mint (`fake-cashu-mint.ts`) that tests, the demo and e2e (`window.__e2eCashuMint`) use instead of a real one. Two rules hold it together:
    - Linky's four tables (`shardPointer`, `setting`, `cashuProof`, `cashuOperation`) are written only by `cashu-shard-store.ts`, always under a Linky owner, and read only by `packages/core/src/modules/cashu/` queries that name their owners; `cashu-table-isolation.test.ts` fails on any other file that names them. Ids, mint URLs and the rows written must match Linky byte for byte; the cross-app vectors in `cashu-cross-app.test.ts` have a twin in Linky's `apps/web-app/src/paykyCashuCrossApp.test.ts`, kept identical.
    - Do not construct a cashu-ts `Wallet` or `Mint` outside `cashu-wallet.ts`: go through `loadCashuWallet`, which caches per mint, talks over `FetchDep` and refuses a mint listing another mint's keyset. cashu-ts is imported lazily there, as the Spark SDK is.
- `apps/web-app/src/core/sentry.ts` wraps `@sentry/react`: enable/disable, the event and breadcrumb scrubbers, and `captureReportedError`. See the project rule above before adding a call site.
- Access control (`packages/core/src/modules/access`, `docs/decisions/access/`) locks screens and actions behind one owner PIN. Every route under `_terminal` declares `staticData.access` — a `Permission` or `"free"`, layouts included — and has no `loader`; `apps/web-app/src/router.test.ts` fails otherwise. ## Domain Module Structure

- Use `*-types.ts` for branded ids, domain enums/unions, and exported domain types.
- Export every part of an id definition, including the raw `id(...)` schema: `export const ItemIdRaw = id("Item")`, `export const ItemId = standardSchemaToZod(ItemIdRaw)`, `export type ItemId = typeof ItemIdRaw.Output`. `*IdRaw` usually has no importer outside its own file — export it anyway. Id definitions are uniform on purpose, so a dead-export scan flagging `*IdRaw` is a false positive; prefer the zod-wrapped `XId` at call sites and in table schemas.
- Use the module root file, for example `payment.ts`, for Evolu table schemas, detail/extension table schemas, indexes, and `InferTable` row exports.
- Use `*-actions.ts` for Evolu mutations and command-style domain operations. Expected domain failures should return `Result`.
- Use `*-queries.ts` for reusable Evolu queries and read models.
- Use `*-utils.ts` for pure domain helpers that are not tied to Evolu mutation execution.
- Split a `*-guards.ts` out of a large `*-actions.ts` when the read-and-validate
  layer has grown its own vocabulary — `bill-guards.ts` holds
  `loadBillStatusSnapshot`/`requireBillInStatus`/`requireEditableBill` and the
  errors they raise, leaving `bill-actions.ts` the mutations, and
  `payment-guards.ts` is the one place a payment's "has money arrived" and
  status are read. Guards read and return `Result`; they never write. Errors
  belong with the half that raises them, which is also what keeps the two
  files from importing each other.
- A module whose errors are raised across several files (actions, guards, preparation) may keep them in one `*-errors.ts`, as `payment-errors.ts` does, together with the Task error unions those files share. A smaller module keeps each error with the half that raises it.
- Keep tests beside the module they cover as `*.test.ts`.
- For aggregate detail/extension tables sharing the root id, keep root and detail table ownership in the same module, and soft delete only the root row — unless the detail clearly owns a separate lifecycle.
- An actions file writes only to tables its own module owns. To write another module's table, compose that module's Task instead of upserting directly, as `bill-actions.ts` does with `bill-line` and `item` actions.
- The intended bill/payment lifecycle — `bill.status` values and transitions, `payment` cancellation/expiry, and how the two combine into a derived paid/underpaid/overpaid coverage — is specified in `docs/bill-payment-states.md`. Read it before changing `bill-guards.ts`, `bill-actions.ts`, `payment-actions.ts`, or any status/coverage derivation between them.

## Domain Action Patterns

- Write every action as an Evolu `Task<T, E, D>` from `@evolu/common` and access dependencies through `run.deps`, as in `payment-actions.ts`. Simple Evolu-only actions typically need `EvoluDep & EvoluOwnerDep`. No curried `(deps) => async (...)` actions.
- In React, obtain runs through `useAppRun()` from `apps/web-app/src/hooks/use-app-run.ts`: `const appRun = useAppRun()` then `await using run = appRun()` inside handlers. Do not call `createRun` directly in components; the sanctioned exceptions are `app-background-jobs.tsx`, which additionally needs `lockManager` and `onError`, and `landing-contact-form.tsx`, which runs on the prerendered landing page where no account or app Evolu exists (`docs/decisions/landing/0002`). Outside React, bootstrap atoms create their own run (`atoms/device-migrations.ts`). For a handler whose only failure UI is a generic toast, prefer `useRunToast()` (`apps/web-app/src/hooks/use-run-toast.ts`) — or `useConfirmedRun()` when a confirm dialog gates it first — over calling `useAppRun()` directly; both own the `await using run = appRun()` scope for you.
- A Task that needs the shared Cashu wallet (`CashuShardStoreDep`, `CashuWalletDep`) runs through `useCashuAppRun()` instead — `await using run = await cashuAppRun()` — or `useCashuRunToast()`. `useAppRun` deliberately leaves the Cashu wallet out and `useCashuAppRun` reads it only when a run is made, so a Cashu wallet that fails to start holds up no other screen; for the same reason `CashuBackgroundJobs` runs the Cashu job apart from `AppBackgroundJobs`, under its own boundary in `App.tsx`.
- Inside an `await using run = appRun()` scope, always `await` calls to `run(...)`/`run.orThrow(...)` before returning — never `return run.orThrow(...)` bare. `await using` disposes `run` as soon as the enclosing function's synchronous execution finishes, so returning the promise unawaited disposes `run` before the task actually completes.
- Outside tests, never discard the `Result` from `run(...)`: either inspect a non-ok result and show the appropriate UI error, or run the Task through `useRunToast()`'s `action` callback, returning a `TranslationKey` for a specific failure message, or nothing (falling off the end) on success — `run.ok`/`run.orThrow` inside that callback throw on failure and `useRunToast` converts the throw into its generic fallback toast. Do not hand-roll `try { await using run = appRun(); await run.orThrow(...) } catch { toast.error(...) }` at a call site; that's exactly what `useRunToast` replaces (inline-edit controls get the same `TranslationKey | undefined` protocol from `useInlineSave` instead). Ignoring `await run(...)` is allowed only in tests.
- Express Task dependencies as intersections of small dependency objects, for example `EvoluDep & SparkWalletDep & FetchDep`.
- In tests, create a concrete deps object with fakes for external services and run Task actions with `await using run = testCreateRun(deps)` followed by `await run(action(...))`.
- When a Task calls another Task, compose it with `await run(otherTask(...))` and propagate non-ok results directly when the error type is part of the caller's error union.
- Keep direct dependency calls for non-Task services, for example `run.deps.evolu.loadQuery(...)` or `run.deps.sparkWallet.create(...)`.
- Define an action's input object type inline in its parameter when only that one function takes it; a single-use `CreateXInput`/`UpdateXInput` alias only sends the reader elsewhere. Name the type when several functions or modules share it (`MarkPaymentPaidInput` across the three `markPaymentPaid*` actions, `CreateAccountTransactionInput` across modules) or when it is a composed type a field would otherwise repeat — not `Parameters<typeof fn>[0]` at the call sites, which ties them to one function's shape.
- For CRDT actions, write tombstones and updates directly without preloading rows, unless current data is required for a domain invariant.
- Pass Evolu mutation payloads through `removeUndefinedValues` to avoid extra or undefined fields.
- When code must wait for an Evolu mutation to complete before running follow-up work, use `runMutationWithCompletion` from `packages/core/src/modules/shared/evolu-utils.ts` instead of hand-rolled `onComplete` promises.
- Minimize the number of `runMutationWithCompletion` batches a Task performs where possible: prefer folding related upserts into one shared batch over several sequential ones, since each batch is an extra awaited round trip and a window where a partial write could be observed. When composing another module's write logic into your own batch, split that module's exports into a load/compute Task (no upsert) and a plain upsert function taking the caller's `MutationOptions`, as `payment-number-actions.ts`'s `loadNextPaymentNumber`/`upsertPaymentNumberRows` do for `createPayment`, instead of calling a Task that always opens its own separate batch.
- In Task code, use `run.deps.console` for all logging. Do not call global `console.log`, `console.warn`, `console.error`, or related console methods directly.
- Clean up disposable resources acquired inside Task actions with `await using`, as with wallet cleanup in `createPreparedPayment`.
- Define domain errors with `defineError` from `packages/core/src/error.ts` and export their types via `ReturnType`, for example `const createPaymentNotFoundError = defineError("PaymentNotFound")<{ readonly id: PaymentId }>()` with `export type PaymentNotFoundError = ReturnType<typeof createPaymentNotFoundError>`. Type each Task's `E` as the union of its expected errors.
- Return `err(createXNotFoundError({ id }))` for missing domain rows or required related records instead of throwing. Use `getFirstOr(rows, error)` from `packages/core/src/modules/shared/result.ts` to turn a load-first query into a `Result`.
- For a React call site invoking a Task whose error type is `never` (its only realistic failure is an unexpected infra error, not a domain `Result`), don't build bespoke pending/error UI: run it through `useRunToast()` (`run.ok(task)` inside the callback) and let the surrounding UI (button, dialog) act optimistically — close/navigate immediately rather than waiting on the mutation. See `move` (the payment-method reorder) in `payment-accounts-settings-page.tsx` and the catalog-item delete confirmation in `item-form-page.tsx` (via `useConfirmedRun()`) for this pattern.

## Translation Key Rules

- Never hardcode user-facing text in React components.
- Add every visible label to `packages/app-shared/src/i18n/en.ts` (through its group file) and translate it in `cs.ts` and `sk.ts`; the `satisfies Record<TranslationKey, string>` checks enforce full coverage.
- Use `t(key, params)` with `{name}`-style placeholders for dynamic values instead of string concatenation.
- Use dot-separated, feature-scoped keys, for example `pay.request`, `settings.language`, or `activity.empty`.
- Do not rename existing translation keys without updating every usage.
- Prefer stable semantic keys over text-derived keys; key names should describe purpose, not exact copy.
- Name the app only through brand placeholders, never "Payky" or "Finito" in copy (`docs/decisions/brand/`): `{appName}` for the nominative and accusative, `{appNameGen}`, `{appNameDat}`, `{appNameLoc}` for the other cases Czech and Slovak decline it into. `t` fills them from the app's brand (`core/app-brand.ts` in each app), so call sites never pass them. Don't put "v/ve" or "s/se" right before a placeholder; reword instead. `packages/app-shared/src/i18n/brand-copy/finito.<language>.txt` shows every branded string as Finito renders it — update it with `vitest -u` and read the diff.

## TypeScript Rules


- Prefer immutability by default:
    - Use `const` unless reassignment is required.
    - Prefer `readonly` fields and `Readonly<...>`/`ReadonlyArray<...>` for read-only data.
    - Return new objects/arrays instead of mutating existing values unless mutation is required by a local API.
- Map a union to a value with a lookup object, not a `switch`:
    - When every branch just returns a value for a union member — an error type to a translation key, a status to a label — declare `const xKeys = { ... } satisfies Record<TheUnion["type"], Value>` and index it (`xKeys[error.type]`). See `earlyConfirmErrorKeys` in `withdraw-flow.ts`.
    - `satisfies Record<...>` is what makes this exhaustive, and it checks *both* directions: a missing member fails to satisfy the type, and a stale key for a member that no longer exists is rejected as an unknown property. A `switch` with a trailing `assertNever` only catches the first, so don't add `assert-never`.
    - Keep a `switch` when branches do more than produce a value (side effects, early returns, differing control flow) or when a case needs the narrowed member rather than just its tag. Make it exhaustive by giving the function an explicit return type, so a missing case fails to compile.
- Use Result-based error handling for expected failures:
    - Import `Result`, `ok`, and `err` from the `@evolu/common` module.
    - Reserve thrown exceptions for programmer errors, schema decode failures, unexpected infrastructure failures, framework boundaries, and established local patterns.
- Prefer `unknown` over `any`:
    - Use `unknown` at untrusted boundaries, then narrow with zod, type guards, or explicit checks.
    - Avoid introducing new `any`. If legacy generic helpers force `any`, keep it local and do not widen public types.
- Prefer `interface` for object shapes.
    - Use `type` for unions, intersections/compositions, mapped or conditional types, function aliases, branded types, and `z.output<...>` aliases.
    - The preference pays where a shape is extended (`interface X extends A, B` is checked once and flags conflicting members, where `A & B` silently yields `never`) or shared across modules. A plain object `type` alias that already exists is not worth converting: an `interface` has no implicit index signature, so it stops being assignable to `Record<string, unknown>`, and same-named interfaces merge silently. Choose `interface` for new shapes; don't churn old ones.
- Prefer `ReadonlyArray<T>` over `T[]` for inputs and read-only collections.
    - Use `T[]` when code intentionally mutates the array, an external/local API requires a mutable array, or a builder/ORM pattern expects mutation.
- Type empty array declarations explicitly.
    - Use `const rows: Row[] = []` or `const rows = [] as Row[]` instead of relying on inference for an empty array.
- Avoid non-null assertions (`!`):
    - Prefer explicit guards, Result errors, zod validation, or control-flow narrowing.
    - Use `!` only when an established framework pattern makes a guard impossible or materially worse, and keep the scope narrow.
    - `noUncheckedIndexedAccess` is enabled, so guard indexed values (`array[index]`, record lookups) with explicit checks, schema parsing, or local assertion helpers rather than adding `!`.
- Use strict equality checks only:
    - Do not use loose equality or inequality (`==` or `!=`), including nullish checks such as `value == null`.
    - Compare explicitly with `===` and `!==`, for example `value === undefined`, `value !== null`, or both checks when both nullish values are possible.
- Avoid mutable parameters:
    - Do not mutate object or array parameters unless the function is explicitly a mutator and the name/signature makes that clear.
    - Prefer returning updated values or passing explicit mutable collaborators such as builders, entity managers, or transactions.
- Avoid circular dependencies:
    - Use type-only imports (`import type`) for types.
    - Keep shared types/helpers in lower-level modules when that matches nearby structure.
    - Do not create barrels or convenience imports that introduce cycles.
- Use utility types from `type-fest` where they clarify intent or match local usage:
    - The ones imported today are `ValueOf`, `Simplify`, `EmptyObject`, `JsonValue`, `ConditionalExcept`, `RequireExactlyOne`, and `RequireOneOrNone`.
    - For mutually exclusive fields (exactly one of a set required, or at most one allowed), use `RequireExactlyOne`/`RequireOneOrNone` instead of hand-writing a union of `?: never` siblings.
    - Do not add a new custom utility type when `type-fest` already provides a clear equivalent.
- Prefer `async`/`await` over `Promise.then(...)` chains.
    - Keep promise combinators such as `Promise.all` when they express concurrency clearly.
    - Keep `Promise.all([...])` tuples reasonably short; if the list grows past 10 items, split it into coherent groups or use another typed pattern.
- Represent money as integer minor units — the branded `Integer`/`NonNegativeInteger` numbers the Evolu schema stores (`payment.amount`, `billLine.totalAmount`) — never floating-point. Convert through the helpers in `packages/core/src/modules/shared/money.ts` (`decimalAmountToMinorUnits`, `minorUnitsToDecimalString`) instead of ad hoc parsing, and take the number of fraction digits from `currencyFractionDigits` rather than assuming two.
- Prefer named exports.
    - Avoid new default exports unless the nearby module family already uses them or a framework requires them, such as Storybook stories or existing framework interop helpers.
